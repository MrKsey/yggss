# yggss — SIP003-плагин для Shadowsocks поверх сети Yggdrasil

[README in English](README.md)

**yggss** — плагин для [Shadowsocks](https://shadowsocks.org) (протокол
[SIP003](https://shadowsocks.org/en/wiki/Plugin.html)), который туннелирует
прокси-трафик через [Yggdrasil Network](https://yggdrasil-network.github.io/) —
полностью шифрованную end-to-end mesh-сеть на IPv6, где каждый узел
идентифицируется своим публичным ключом ed25519, а не IP-адресом.

Обе стороны туннеля (клиент и сервер) работают как yggdrasil-узлы в
библиотечном режиме — без TUN-адаптера, без root, без системных маршрутов.
Данные передаются по QUIC-стримам поверх шифрованной end-to-end сессии
yggdrasil:

```
приложения > ss-local > yggss (клиент) == mesh yggdrasil / direct UDP == yggss (сервер) > ss-server > интернет
```

- **Адресация по ключу узла**: сервер доступен по своему публичному ключу,
  а не по IP. Если прямая доступность заблокирована — трафик идёт через
  mesh-пиров.
- **Маскировка**: для внешнего наблюдателя трафик выглядит как обычный
  yggdrasil-пирринг — сессии TLS/QUIC/WebSocket к известным публичным пирам
  плюс «браузерный» HTTP/3-поток к серверу.
- **Многослойное шифрование**: TLS на линке + end-to-end сессия yggdrasil +
  QUIC/TLS внутри.
- **Мультиплексирование**: одно QUIC-соединение, по стриму на каждое
  проксируемое TCP-соединение.

Готовые бинарники для **Linux x64, Linux arm64 и Windows x64** прилагаются
к каждому [релизу](https://github.com/MrKsey/yggss/releases).

## Как это работает

1. **Оба плагина создают yggdrasil-узел** (`core.New` из yggdrasil-go,
   библиотечный режим). У каждого узла есть ed25519-идентичность: приватный
   ключ (секрет) и публичный ключ (адрес узла в mesh).
2. **Серверный плагин** слушает линк-подключения yggdrasil на публичном
   эндпоинте (`SS_REMOTE_HOST:SS_REMOTE_PORT`) и поднимает QUIC-листенер
   поверх пакетной сессии узла. Каждый принятый QUIC-стрим форвардится
   на локальный `ss-server`.
3. **Клиентский плагин** устанавливает пирринг с сервером (прямой линк к
   `SS_REMOTE_HOST:SS_REMOTE_PORT`, опционально плюс публичные пиры), затем
   dial'ит сервер *по ключу* через mesh. Каждое соединение ss-local —
   отдельный QUIC-стрим.
4. **Аутентификация**: клиент пинит публичный ключ сервера (проверяется
   внутри QUIC-handshake); сервер может сверять ключи клиентов с белым
   списком; group password ограничивает, кто вообще может пирриться на
   уровне линка.
5. **Путь данных**: TCP-стрим ss-local -> QUIC-стрим -> (direct UDP или
   сессия yggdrasil) -> accept на сервере -> TCP к ss-server.

## Маскировка трафика

Линки yggdrasil и так выглядят как обычные TLS/WebSocket-сессии. Сверх того,
режим *direct* имитирует браузер:

- **ALPN зафиксирован в `h3`** — стандартный идентификатор HTTP/3. QUIC
  Initial-пакет шифруется общеизвестным ключом (RFC 9001), поэтому DPI видит
  ClientHello; уникальная ALPN-строка была бы мгновенной сигнатурой, а `h3`
  шлют все браузеры.
- **Фейковый SNI** (опция `sni`) подставляется и в ClientHello TLS-линка, и в
  ClientHello QUIC — handshake выглядит как настоящее соединение к популярному
  домену.
- **Transport-параметры** (лимиты стримов, размер начального пакета)
  подобраны под HTTP/3-профиль Chrome — quic-go fingerprint не выбивается.
- **Гонка h2 -> h3 (модель Alt-Svc)**: пользовательский трафик никогда не
  ждёт быстрый путь. Mesh-канал обслуживает соединения сразу, а фоновый
  пробник верифицирует QUIC-путь *только пока mesh-канал активен* — UDP-трафик
  не существует без параллельной TCP-сессии, в точности как браузер, гоняющий
  HTTP/3 наперегонки с HTTP/2. Проба удалась — новые стримы уходят в QUIC;
  провалилась — мгновенный откат на mesh.

```
tunnel: h3 path verified in 95ms (probe rtt) - new streams upgrade to QUIC
tunnel: h3 probe round trip failed (context deadline exceeded) - 1 of 2 before downgrading
tunnel: h3 path failed (2 consecutive probe errors: ...) - downgrading to h2, existing streams reconnect via mesh
tunnel path: h2+h3 (direct verified) - active: direct QUIC
tunnel path: h2 (h3 failed, probing) - active: mesh
```

### Стартовая сводка

Первые строки лога всегда показывают версию и четыре параметра, определяющие
роль плагина — работающий экземпляр можно опознать по одному логу:

```
yggss v1.2.0
bind: [::1]:40729
destination: [2001:db8::1]:443
scheme: tls
mode: direct
```

### Что означает лог

| Строка лога | Значение |
|---|---|
| `tunnel: h3 path verified in <rtt> - new streams upgrade to QUIC` | direct-путь прошёл реальную round-trip пробу; новые соединения идут по direct QUIC |
| `tunnel: h3 probe error on a living connection (...) - 1 of 2 before downgrading` | сбой пробы (например, один потерянный пакет); не критично, QUIC ретранслирует |
| `tunnel: h3 probe round trip failed (...) - 1 of 2 before downgrading` | путь перестал пропускать данные (чёрная дыра); ещё один сбой — и канал переключится |
| `tunnel: h3 path failed (...) - downgrading to h2, existing streams reconnect via mesh` | direct-канал сброшен: новые стримы идут по mesh, стримы на умершем соединении мгновенно получают ошибку, и их приложения переподключаются |
| `tunnel: h3 probe rtt ... exceeds the degradation threshold` | растут потери (всплеск RTT относительно базлайна пути); путь уступает mesh |
| `tunnel: h3 verify cache expired - probing the path again` | истёк TTL verified-кэша; путь перепроверяется до возобновления апгрейдов |
| `tunnel: idle, h3 cache dropped - will re-verify on next activity` | долго не было трафика; проба приостановлена и перепроверит путь при следующей активности |
| `tunnel path: ... - active: direct QUIC` / `active: mesh` | что несёт трафик прямо сейчас (периодический статус-лог) |
| `server identity verified: peered node key matches server_key` | mesh-peering с сервером поднят, его ключ совпадает с конфигом |

## Режимы туннеля

Опция `mode` выбирает, что переносит стримы туннеля между клиентским и
серверным плагином:

- **`direct`** — это, по сути, **QUIC поверх обычного UDP, минуя Yggdrasil
  целиком**. Клиент напрямую диалит UDP-эндпоинт сервера; пакеты ходят ровно
  как HTTP/3-трафик браузера — один QUIC-handshake, TLS 1.3 внутри QUIC, без
  mesh-маршрутизации и лишней инкапсуляции. Идентичность узлов Yggdrasil
  по-прежнему используется для аутентификации (TLS-сертификаты в QUIC — это
  ed25519-ключи узлов), но сам *транспорт* к сети Yggdrasil отношения не
  имеет: ни spanning tree, ни транзитные пиры, ни сессионный слой. Поэтому
  он быстрый: один криптослой вместо трёх и никаких накладных на
  маршрутизацию.
- **`mesh`** гоняет QUIC поверх настоящей end-to-end сессии Yggdrasil.
  Клиент диалит *публичный ключ* сервера, а Yggdrasil маршрутизирует пакеты —
  напрямую через TCP/TLS-линк, когда это возможно, иначе через mesh-пиры.
  Это добавляет два криптослоя (линк-TLS + end-to-end сессия) и хопы
  маршрутизации, но работает даже когда у сервера нет доступного
  UDP-эндпоинта, и маршрут может идти через публичные пиры.

| | `mesh` (по умолчанию) | `direct` |
|---|---|---|
| Транспорт | QUIC поверх сессии Yggdrasil | QUIC поверх обычного UDP (Yggdrasil не участвует в передаче данных) |
| Адресация | публичный ключ сервера, маршрутизация через mesh | IP:порт сервера, прямое соединение |
| Криптослоёв | 3 (линк-TLS + сессия + QUIC) | 1 (встроенный TLS 1.3 внутри QUIC) |
| Типичная скорость | ниже (см. ниже) | в 2–3 раза выше |
| Работает через mesh-пиры | да | нет (нужна прямая UDP-доступность) |
| Автооткат на mesh | — | да, в стиле Alt-Svc |

В режиме `direct` сервер слушает QUIC/UDP на том же порту, что и TLS-линк
(TCP и UDP независимы). Аутентификация не меняется: те же ключи узлов
проверяются внутри QUIC-handshake.

## Почему скорость через mesh может быть низкой

Пропускная способность mesh ограничена архитектурными особенностями самого
Yggdrasil:

1. **Лишние слои шифрования и инкапсуляции.** Каждый байт полезной нагрузки
   шифруется трижды (линк-TLS, end-to-end сессия, QUIC) и оборачивается
   в несколько заголовков. Стоимость CPU на байт примерно в 2–3 раза выше,
   чем в direct-режиме.
2. **Маршрутизация yggdrasil оптимизирует латентность, а не полосу.**
   Spanning-tree выбирает *ближайший* путь, а не *самый широкий*. Маршрут
   с малой задержкой через несколько публичных пиров может иметь куда меньшую
   ёмкость, чем один прямой линк.
3. **Транзитный трафик.** Yggdrasil по дизайну релеит чужой трафик через
   дерево, и отключить это нельзя. Публичные пиры (и ваш узел, если у него
   есть публичные пирринги) могут нести чужой трафик, деля с вами канал
   и CPU. yggss детектирует это и предупреждает в статус-логе:

   ```
   mesh transit: ~30MiB of third-party traffic relayed in the last interval (100% of link traffic) - yggdrasil relays transit by design; trimming the peers list reduces it
   ```

   Единственная практическая мера — сократить список `peers`.
4. **Ёмкость публичных пиров.** Комьюнити-пиры общие для всех и часто
   ограничены по скорости.

**Рекомендация**: используйте `direct`, если у сервера открыт UDP; mesh
держите как автоматический резерв (он всегда горячий — откат мгновенный).

### Быстрое переключение при деградации direct-пути

Клиент непрерывно следит за direct-путём и переключает каналы по признакам
деградации, а не по факту смерти:

- фоновая проба посылает реальный round-trip запрос (сервер возвращает эхо);
  путь, глотающий пакеты (смена NAT-маппинга, firewall начавший резать UDP),
  проваливает пробу за 3 секунды, даже если QUIC-соединение формально
  «открыто» — direct-соединение закрывается немедленно, стримы на нём
  мгновенно получают ошибку, и их приложения переподключаются уже по mesh;
- резкий рост RTT относительно собственного базлайна пути (или две ошибки
  подряд) трактуется как рост потерь и переключает так же;
- при закрытии direct-соединения (рестарт сервера, смена сети) переключение
  происходит в тот же момент, а не по таймаутам QUIC;
- в деградировавшем состоянии проба повторяется каждые несколько секунд;
  как только пробы снова чистые — новые стримы возвращаются в QUIC.

Одиночный потерянный пакет переключения не вызывает — QUIC ретранслирует
его прозрачно.

## Быстрый старт

### 1. Сгенерируйте ключи узлов

```bash
./yggss -genkey
```

```
private key (hex):  1d62c1...b71
public key (hex):   c6e500...b71
yggdrasil address:  200:7235:ff73:d8a4:a4af:224a:7649:c0d4
```

Сгенерируйте одну пару для сервера и по одной для каждого клиента.
Приватный ключ — идентичность узла, храните его в секрете.

### 2. Куда вводить параметры

Три эквивалентных способа, по возрастанию приоритета:

1. **JSON-конфиг** (рекомендуется) — см. [`examples/`](examples/);
2. **Флаги командной строки** (`-key`, `-serverkey`, ...) для автономного
   запуска;
3. **Строка `plugin_opts`** при работе под shadowsocks
   (`key=...;serverkey=...;password=...`).

Под shadowsocks адреса `bind`/`destination` подставляются из SIP003-окружения
автоматически; конфиг несёт только ключи, пиры и тюнинг. Достаточно передать
путь к конфигу:

```jsonc
"plugin_opts": "/etc/shadowsocks/yggss-client.json"      // полная форма
"plugin_opts": "c=/etc/shadowsocks/yggss-client.json"    // короткая форма
"plugin_opts": "s;c=/etc/shadowsocks/yggss-server.json"  // "s" = режим сервера
```

### 3. Примеры конфигурации

Клиентский плагин (`examples/yggss-client.json`):

```json
{
	"server": false,
	"bind": "127.0.0.1:1080",
	"destination": "<IP_СЕРВЕРА>:4440",
	"key": "<ПРИВАТНЫЙ_КЛЮЧ_КЛИЕНТА_HEX>",
	"server_key": "<ПУБЛИЧНЫЙ_КЛЮЧ_СЕРВЕРА_HEX>",
	"password": "<ОБЩИЙ_СЕКРЕТ_ГРУППЫ>",
	"scheme": "tls",
	"mode": "direct",
	"timeout": 30,
	"log_interval": 30,
	"failover": true,
	"peers": [
		"wss://<ПУБЛИЧНЫЙ_ПИР_1>:443/path",
		"tls://<ПУБЛИЧНЫЙ_ПИР_2>:порт"
	]
}
```

Серверный плагин (`examples/yggss-server.json`):

```json
{
	"server": true,
	"bind": ":4440",
	"destination": "127.0.0.1:8388",
	"key": "<ПРИВАТНЫЙ_КЛЮЧ_СЕРВЕРА_HEX>",
	"client_keys": ["<ПУБЛИЧНЫЙ_КЛЮЧ_КЛИЕНТА_HEX>"],
	"password": "<ОБЩИЙ_СЕКРЕТ_ГРУППЫ>",
	"mode": "direct",
	"log_interval": 30
}
```

Полные сценарии, включая конфиги shadowsocks-rust и systemd-юниты, — в
каталоге [`examples/`](examples/).

### 4. Справочник опций

| Ключ | Сторона | Описание |
|------|---------|----------|
| `s` | сервер | Режим сервера |
| `key` | оба | Приватный ключ узла (hex, из `-genkey`) |
| `serverkey` | клиент | Публичный ключ серверного узла (hex) — обязателен |
| `clientkey` / `client_keys` | сервер | Разрешённые публичные ключи клиентов (белый список; пусто = любой узел) — необязательно: достаточно совпадающего `password` с обеих сторон, белый список лишь добавляет поузловой контроль доступа |
| `peers` | оба | Дополнительные пиры yggdrasil через запятую (`tls://`, `tcp://`, `quic://`, `ws://`, `wss://`, `socks://`, `sockstls://`; параметры линка `?key=`, `?priority=`, `?sni=`, `?password=`, `?maxbackoff=`) |
| `password` | оба | Group password yggdrasil (общий секрет) — простейшая схема: `key` + `password` на сервере и `key` + `serverkey` + `password` на клиенте, без белых списков ключей |
| `scheme` | оба | Схема прямого линка: `tls` (по умолчанию), `tcp`, `quic`, `ws`, `wss` |
| `t` / `timeout` | клиент | Таймаут установления туннеля, сек (по умолчанию 30) |
| `loginterval` / `log_interval` | оба | Интервал статус-лога, сек (по умолчанию 30, `0` = выкл) |
| `failover` | клиент | Отказоустойчивость прямого линка (по умолчанию вкл при заданных пирах) |
| `failover_latency` | клиент | Порог латентности прямого линка, мс (по умолчанию 1000) |
| `failover_check` | клиент | Интервал проверки, сек (по умолчанию 5) |
| `mode` | оба | `mesh` (по умолчанию) или `direct` |
| `sni` | клиент | Фейковый домен для ClientHello прямого линка |
| `direct_dial_timeout_sec` | клиент | Таймаут direct-диала по UDP (по умолчанию 5) |
| `direct_retry_sec` | клиент | Интервал переподтверждения direct-пути (по умолчанию 10) |

Те же опции доступны флагами командной строки (`-s`, `-key`, `-serverkey`,
`-clientkey`, `-peers`, `-password`, `-scheme`, `-t`, `-b`, `-d`, `-sni`,
`-mode`, ...) для автономного запуска.

  содержит `yggss-linux-amd64`, `yggss-linux-arm64` и

  ```bash
  GOOS=linux   GOARCH=amd64 CGO_ENABLED=0 go build -trimpath -ldflags "-s -w" -o yggss-linux-amd64 .
  GOOS=linux   GOARCH=arm64 CGO_ENABLED=0 go build -trimpath -ldflags "-s -w" -o yggss-linux-arm64 .
  GOOS=windows GOARCH=amd64 CGO_ENABLED=0 go build -trimpath -ldflags "-s -w" -o yggss.exe .
  ```

Один бинарник работает и как клиент, и как сервер; роль задаётся полем
`"server"` в JSON-конфиге (или флагом `-s`).

## Где взять список актуальных пиров

Поддерживаемый сообществом список открытых пиров Yggdrasil:
<https://github.com/yggdrasil-network/public-peers> — выберите 2–3 записи
географически близкие к вам и добавьте в `peers`. Не добавляйте много:
каждый публичный пирринг — потенциальный транзитный путь (см. *Почему
скорость через mesh может быть низкой*). С настроенным group password
чужие узлы не смогут пирриться с вашими листенерами, даже если обнаружат их.

## Ограничения

- SIP003 передаёт только TCP; UDP через плагин невозможен (ограничение
  протокола плагинов shadowsocks).
- Первое соединение после старта может устанавливаться несколько секунд,
  пока yggdrasil находит маршрут до ключа сервера (заметнее всего через
  публичные пиры).
- Долгоживущие стримы, открытые через direct-путь, обрываются при смерти
  QUIC-соединения (стримы не переносятся между транспортами); приложения
  переподключаются сами, новые стримы мгновенно идут через mesh.
- yggdrasil-go лицензирован под LGPLv3 (с оговоркой для статической
  линковки).

## Тесты

```bash
go test ./...
```

- Юнит-тесты и тесты state-machine покрывают логику выбора каналов
  (жизненный цикл, деградация/восстановление, fail-fast) на подменных
  QUIC-соединениях.
- `TestLiveCutover` — fault-injection сценарий: реальный QUIC поверх UDP через
  управляемый прокси-«обрыв» плюс настоящий yggdrasil mesh-peering. Прогоняет
  полную матрицу отказов/восстановлений — direct работает, чёрная дыра UDP
  (переключение на mesh), UDP восстановился (апгрейд обратно), сломаны оба
  канала (стримы фейлятся быстро), восстановились оба (трафик пошёл без
  перезапуска клиента).
